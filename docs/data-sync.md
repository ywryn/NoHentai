# 服务器每日同步

调度由常驻 `nohentai-worker` 每十秒检查 SQLite 的 `schedules`，不再依赖 GitHub Actions 或 Vercel。收藏、标签词典、每日搜索可独立启停并设置小时、分钟、时区；默认全部关闭，默认时间北京时间 04:00。先在后台配置并测试服务，再手动启用。错过的到期任务在 worker 恢复时补排一次，之后计算下一次时间。

旧 `nohentai-sync.timer` 保留为维护兼容，生产应保持 disabled，避免与数据库调度重复。每天数据库备份仍由 `nohentai-backup.timer` 执行。

## 队列和发布

后台“运行全部”分别排队三个独立任务，某项失败不阻塞其他项发布。每日规则可以仅执行某个分组。CLI `enqueue all` 保留旧的一体任务，全部步骤成功才一次发布。

1. 排队时冻结规则版本及所需收藏来源参数，凭证快照加密，不向前端返回。
2. worker 串行领取，子进程执行，上限六小时；开始前一致性备份。
3. 收藏 / 标签词典 / 每日抓取分步骤保存结果与进度检查点。
4. 发布前再次检查取消、规则版本与数据完整性，一个事务提交结果与版本。

抓取期间不占用数据库写锁。取消运行任务会终止子进程；提交之前取消保留旧数据。worker 重启将中断任务标为失败，排队任务继续。按“当前配置重跑”重新抓取；按“原配置续跑”使用原凭证和规则，复用已成功步骤。若规则变更或收藏检查点已过时，会拒绝发布并要求当前配置重跑。只保留最近十个成功任务的大结果，失败任务检查点保留供重试，按规模安排归档。

每日单分组发布保留其他组。全部每日任务在任意规则变化后拒绝发布。人工覆盖、书单和服务配置不会被同步覆盖。

## 完整性保护

收藏 HTTP 错误、空列表、分页循环、重复画廊、缺失元数据批次都会失败。比当前数据库减少超过 20% 时拒绝提交；每日搜索缺失详情、重复条目、分页循环也拒绝部分结果。失败保留最近完整数据。上游原始错误、Cookie 和响应体不写入后台结果。

确认主动批量取消收藏时，先备份、停止常驻 worker，由本机维护人员执行 `sync favorites --allow-favorites-shrink` 显式放行，见 [部署文档](vultr-deployment.md)。环境变量不绕过保护。

同步不写入仓库的 `web-static/public/data`，这些文件只用于初次导入。生产内容来自 SQLite。

```sh
# 本地开发或已加载生产环境变量的终端
.venv/bin/python -m backend.cli enqueue favorites
.venv/bin/python -m backend.cli worker --once
```

`worker --once` 仅在无常驻 worker 时使用，单实例文件锁防止重复领取。没有凭证时不要启用调度。自动测试模拟上游，不证明实际 Cookie / 付费服务可用。

任务实时明细入口为“运行记录 → 日志与进度”，每两秒读取 SQLite job_events 新事件。每日各分组的分页与元数据批次、收藏分页、失败批次重试和事务发布均记录安全明细；进度只有已知总批次时显示百分比。旧任务没有的日志不会补造。
